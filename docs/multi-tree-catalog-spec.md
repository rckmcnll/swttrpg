# Spec: Multiple Specializations & Force Powers + F&D Catalog

**Status:** Proposed (design only — not yet implemented)
**Target file:** `force-and-destiny-character-sheet.html`
**New files:** `fad-catalog.js`, `tools/convert-catalog.mjs`, this spec
**Schema impact:** additive (no `STORAGE_KEY` / state-schema bump)

---

## 1. Context & goal

The Force & Destiny character sheet is a self-contained, offline (`file://`) HTML app that autosaves to
`localStorage`. Today it ships exactly **one** specialization tree (Shadow) and **one** Force power tree
(Misdirect), hard-baked into `DEFAULT_STATE.trees`. There is **no way to add other specializations or
Force powers**, and **no library** of F&D content to choose from — every tree must be hand-authored in the
data blob.

A real F&D character normally has **multiple specializations** (starting career spec + purchased specs,
possibly universal specs) and **multiple Force powers**. The goal of this work is to let a user **add and
remove any number of specializations and Force powers** from a built-in catalog, with **XP automatically
tallied and validated** across all trees.

**Already in place (no work needed):** `state.trees` is an array and `renderTrees()` already loops over
every entry, choosing the heading from `tree.kind`. Multiple trees therefore already *render* correctly if
present. What is missing is: (1) a **catalog** of all F&D specs/powers, (2) **add/remove UI**, and
(3) **cross-tree XP tallying**.

### Confirmed product decisions
1. **Storage** — the catalog ships as a separate **`fad-catalog.js`** loaded via `<script src>`. `fetch()` of
   a `.json` is CORS-blocked under `file://`, but a classic `<script>` tag loads from disk fine. The sheet
   becomes a **2-file bundle** (HTML + catalog) rather than a single portable file.
2. **Scope** — target the **full** F&D catalog (all 6 careers' specializations + universal specializations +
   all Force powers), generated by a **converter from an OggDude DataSet (XML)** rather than hand entry.
3. **XP** — **auto-tally + validate**: sum purchased node costs across all trees, derive Available XP, and
   warn on overspend.

## 2. Current data model (verified)

```
state = { schema, fields{}, skills[], tables{}, trees[], source }
```
- `STORAGE_KEY = "sael_dara_fad_sheet_v3"`, `state.schema = "sael-dara-sheet-state-v3"`.
- **Tree:** `{ key, name, kind:'specialization'|'force_power', columns:4, nodes[], edges[], source? }`.
- **Node:** `{ id, key, name, row, column, span, cost, purchased, pathState, activation, ranked, forceTalent, description, notes }`.
- **Edge:** `{ from, to, direction:'down'|'right' }`.
- **Locking:** `incomingMap(tree)` builds `to → [from]`; `statusFor(tree,node)` returns
  `purchased | available | locked` (available if a node has no incoming edges, or any incoming prerequisite
  is purchased).
- `renderTrees()` clears `#tree-container` and rebuilds every `.tree-block`. `updateTreeSpent()` sums
  purchased costs **per tree** into `.tree-spent`; there is **no** cross-tree total.
- `recalcEncumbrance()` is the precedent pattern for "compute a value → write `state.fields.X` → reflect to
  `[data-field="X"]` inputs as `readOnly` with a title".
- `mergeState()` **wholesale-replaces** `trees`. `migrateState()` runs after `load()` with idempotent
  `=== undefined` guards (e.g. `encThrManual`). `importBackup()` does **not** currently call `migrateState()`.
- There is **no** add/remove-tree UI and **no** `xpSpent` input in the markup (only `xpTotal` / `xpAvail` on
  the identity row). Only Shadow + Misdirect tree data exist anywhere in the repo.

Reference data: `sael_dara_redesigned_sheet_state_equipment_print_fixed.json` matches the runtime `trees`
shape; `sael_dara_complete_character_equipment_print_fixed.json` carries OggDude-shaped `catalog_record`
(`TalentRows`/`Directions`, `AbilityRows`) — the converter's reference for field mapping.

## 3. Catalog schema — `fad-catalog.js`

A **classic script** (not a module) that assigns one frozen global:

```js
window.FAD_CATALOG = Object.freeze({
  schema: "fad-catalog-v1",   // distinct from the sheet's state schema
  version: 1,                  // bump when output shape changes
  generatedAt: "<ISO>",       // diagnostic only
  source: "OggDude DataSet (user-supplied)",
  careers: { /* keyed by career key */ },
  specializations: { /* keyed by spec key, includes universals */ },
  forcePowers: { /* keyed by power key */ }
});
```

### 3.1 Top-level maps (retrieval-optimized)
```js
careers: {
  CONSULAR: { key:"CONSULAR", name:"Consular", specializations:["HEALER","NITHER","SAGE", ...] },
  GUARDIAN, MYSTIC, SEEKER, SENTINEL, WARRIOR
}
specializations: {            // career:null => universal (e.g. Force-sensitive Exile, etc.)
  SHADOW: <specTemplate>, ARTISAN: <specTemplate>, ...
}
forcePowers: {
  MISDIRECT: <powerTemplate>, MOVE: <powerTemplate>, ...
}
```
`careers[*].specializations[]` provides the **picker grouping + ordering**. The **Universal** group is
*derived* by scanning `specializations` for `career === null` (single source of truth = each spec's own
`career`; no parallel list to keep in sync). All keys are uppercase OggDude keys for stable identity.

### 3.2 Specialization template
```js
{ key:"SHADOW", name:"Shadow", kind:"specialization",
  career:"SENTINEL" | null,                 // null => universal
  careerSkills:["Skulduggery","Stealth","Streetwise","Underworld"],
  source:"Force and Destiny Core Rulebook",
  columns:4, nodes:[ /* nodeTemplate */ ], edges:[ /* edgeTemplate */ ] }
```

### 3.3 Force-power template
```js
{ key:"MISDIRECT", name:"Misdirect", kind:"force_power",
  career:null,                              // field kept for shape parity
  source:"...", columns:4, description:"<power-level prose>",
  nodes:[ /* nodeTemplate */ ], edges:[ /* edgeTemplate */ ] }
```

### 3.4 Node template (stateless)
Catalog nodes carry **only** template fields — never `purchased`, `notes`, or `pathState`:
```js
{ id:"shadow_r1c1_sleightmind", key:"SLEIGHTMIND", name:"Sleight of Mind",
  row:1, column:1, span:1, cost:5,
  activation:"Passive",                     // "" if none
  ranked:false, forceTalent:false,
  description:"...",
  upgrade:"basic"                           // force_power nodes only: basic|control|magnitude|strength|duration|range
}
```
Field names match the **runtime** node shape (`span`, `cost`, `ranked`, `forceTalent`) — *not* the verbose
`column_span`/`cost_xp` form in the complete-character JSON — so instantiation is a pure clone with no
field remapping. `upgrade` is metadata only (optional UI tinting); it does **not** affect locking, which
stays edge-driven.

### 3.5 Edge template
```js
{ from:"shadow_r1c1_sleightmind", to:"shadow_r2c1_wellround", direction:"down" }   // 'down' | 'right' only
```

### 3.6 Catalog → runtime mapping
| runtime field | source |
|---|---|
| `key, name, kind, columns, nodes[*] template fields, edges[]` | deep clone of template |
| `nodes[*].purchased` | set `false` |
| `nodes[*].notes` | set `''` |
| `nodes[*].pathState` | set `'available'` (recomputed live by `statusFor`; stored for export fidelity) |
| `instanceId` | newly generated (§4.1) |
| `catalogKey` | = template `key` (for dedupe / "already added" checks) |
| `career, careerSkills, upgrade` | carried through (harmless; enables career-skill note + future UI) |

The runtime tree is a **self-contained copy**, so regenerating the catalog never mutates saved characters.

## 4. Instantiation & removal

### 4.1 Add
`addSpecialization(specKey)` and `addForcePower(powerKey)` both delegate to `instantiateTree(template)`:
1. Guard: if `!window.FAD_CATALOG` → `flash('Catalog not loaded', true)`; return.
2. Lookup template by key; if missing → flash + return.
3. **Dedupe** (§4.3); if already present → flash + return.
4. `const tree = clone(template)` (reuse existing deep-clone helper).
5. `tree.catalogKey = template.key; tree.instanceId = makeInstanceId(template.key);`
6. For each node: `purchased=false; notes=''; pathState='available'`.
7. **Suffix node ids + edge endpoints** with `'__'+instanceId` (§4.2).
8. Insert at the ordered position (§4.4): `state.trees.splice(pos, 0, tree)`.
9. `renderTrees(); recalcXp(); scheduleSave();`

`makeInstanceId(key)` = `key.toLowerCase() + '_' + Date.now().toString(36) + Math.random().toString(36).slice(2,6)`,
**stored** on the tree so it is stable across reloads.

### 4.2 Node-id uniqueness
`incomingMap`/`statusFor` are rebuilt **per tree**, so cross-tree id collisions are harmless today. Suffixing
is still applied on instantiation (future global lookups + DOM `data-node-id` uniqueness): build
`idMap[oldId] = oldId + '__' + instanceId`, rewrite every `node.id` and every `edge.from`/`edge.to`
atomically. Legacy trees keep their original ids (not retro-suffixed).

### 4.3 Dedupe
- **Specializations:** no duplicates — block if any existing tree has `kind==='specialization'` and
  `(t.catalogKey ?? t.key) === specKey`.
- **Force powers:** each added at most once — same check with `kind==='force_power'`.
- The picker also **disables** already-added entries (§5); dedupe here is a defense-in-depth backstop.

### 4.4 Ordering
Specializations grouped **before** Force powers; add-order preserved within each group. `treeInsertIndex(kind)`:
power → end of array; spec → just after the last existing specialization. An optional **stable** re-sort by
kind on load normalizes legacy ordering.

### 4.5 Remove
`removeTree(instanceId)` (fall back to index for legacy trees): `confirm('Remove "<name>"? Purchased XP on
this tree will no longer count.')` → `splice` → `renderTrees(); recalcXp(); scheduleSave()`. No undo
(consistent with `clearSheet`/`resetDefaults`); export-first is the safety net.

## 5. UI (all new controls `.no-print`)

- **`#treeControls`** bar — a **sibling immediately above** `#tree-container` (never inside it; `renderTrees`
  clears the container): `+ Add specialization` and `+ Add Force power` buttons (reuse `.btn.ghost`).
- **`openTreePicker(mode)`** builds a lightweight `#treePicker` popover/modal fresh each open:
  - `mode='spec'` → one `<section>` per career in fixed order (Consular, Guardian, Mystic, Seeker, Sentinel,
    Warrior), each listing its spec keys, then a synthetic **"Universal"** section (`career===null`).
  - `mode='power'` → flat list of `forcePowers` (alphabetical; optional tier grouping later).
  - Each entry is `<button class="picker-item" data-key="...">Name</button>`; **already-added** entries render
    `disabled` with an `(added)` suffix; dismiss on backdrop click / `Esc`.
- **Per-tree × remove** button appended to `.block-head` in `renderTrees` (reuse `.mini-btn.clear` styling),
  marked `.no-print`; wired to `removeTree(tree.instanceId ?? tidx)`.
- **Catalog-absent guard:** if `typeof window.FAD_CATALOG === 'undefined'`, the Add buttons are `disabled` with
  a tooltip ("fad-catalog.js not loaded") and the sheet otherwise behaves exactly as today — single-file
  behavior is preserved if the catalog file is missing.

Only two edits to `renderTrees`: add the × button to the head template + wire its `onclick`. Wire the new
buttons in the existing `DOMContentLoaded` block alongside current button wiring.

## 6. XP automation (mirrors `recalcEncumbrance`)

```js
function recalcXp(){
  const spent = state.trees.reduce((s,tree)=>
    s + tree.nodes.reduce((a,n)=> a + (n.purchased ? Number(n.cost||0) : 0), 0), 0);
  state.fields.xpSpent = String(spent);
  const total = numberVal(state.fields.xpTotal, 0);
  const avail = total - spent;
  state.fields.xpAvail = String(avail);
  document.querySelectorAll('[data-field="xpSpent"]').forEach(el=>{ el.value=state.fields.xpSpent; el.readOnly=true; el.title='Sum of purchased node costs across all trees.'; });
  document.querySelectorAll('[data-field="xpAvail"]').forEach(el=>{ el.value=state.fields.xpAvail; el.readOnly=true; el.title='Total XP minus spent XP.'; });
  updateXpWarning(avail);
  return spent;
}
```
- **Add a read-only `xpSpent` input** to the XP/identity row (only `xpTotal`/`xpAvail` exist today). If the
  owner prefers no new field, `recalcXp` still writes `state.fields.xpSpent` for export and reflects `xpAvail`.
- **`updateXpWarning(avail)`** toggles a `.no-print` `#xpWarning` span ("Overspent by N XP") and a
  `.field-error` class on `xpAvail` when `avail < 0` (reuse the existing `.danger` accent).
- **Call sites:** node purchase toggle (inside the node `onclick`, once), end of add/remove, `bindFields` when
  `key==='xpTotal'` (parallels `cBrawn → recalcEncThreshold`), and in `renderEverything()` after `renderTrees()`.

### FFG rules nuances
- **Career skills granted by a specialization** — do **not** auto-apply in v1 (would fight manual skill edits
  and conflict across multiple specs). Surface `careerSkills` as a read-only note/tooltip on the tree block.
  *(Future enhancement.)*
- **Additional-specialization surcharge** (10 × specs-already-owned, the first/career spec being free) — not
  represented by any node. Recommended: optional auto-surcharge gated by `state.fields.xpAutoSpecSurcharge`
  (default `true`) folded into `recalcXp`; **or** ship as a manual note for minimal scope. Must not charge the
  starting specialization.

## 7. Persistence & migration

- **Do NOT bump** `STORAGE_KEY` / `state.schema` — all changes are additive; bumping would orphan the user's
  existing autosave.
- **Extend `migrateState()`** (idempotent `=== undefined` guards):
  1. For each tree lacking `instanceId`: `tree.instanceId = makeInstanceId(tree.key||'tree')`;
     `tree.catalogKey = tree.catalogKey ?? tree.key`.
  2. Default new fields: `xpSpent='0'`, `xpAvail` (recomputed), `xpAutoSpecSurcharge=true`.
  3. Optional stable re-sort of `state.trees` by kind (spec before power).
- **`exportBackup`** needs no change (new fields ride along). **Add `migrateState()` to `importBackup`** before
  `renderEverything()` so imported legacy trees get ids/defaults.
- The **catalog is never part of saved state or backups** — only the chosen, instantiated trees are. A saved
  character can reference a spec the catalog later renames/removes; that's fine because runtime trees are
  self-contained copies (do not re-resolve against the catalog at render time).
- `mergeState`'s wholesale `base.trees = inc.trees` stays correct (a loaded/imported state should fully define
  its trees, not merge node-by-node).

## 8. OggDude converter (dev-only build step)

- **Inputs (user-supplied DataSet `Data/` folder — NOT committed):** `Specializations.xml`, `Talents.xml`,
  `ForcePowers.xml`, `Careers.xml`.
- **Specializations:** `TalentRows` is row-major over a 4-column grid. For row `r`, column `c`:
  resolve `row.Talents[c]` against `Talents.xml` for `name`, `ActivationValue`→`activation`,
  `Ranked`/`ForceTalent`→bools, `Description`. Node `cost = Number(row.Cost)`. Emit edges from `Directions[c]`
  using **only** `Down`/`Right` (Up/Left are reciprocals of a neighbor's Down/Right — emitting both duplicates
  edges and mis-keys `incomingMap`).
- **Force powers:** `AbilityRows` has parallel arrays `Abilities[] / Directions[] / AbilitySpan[] / Costs[]`.
  Skip blank cells (`""`); **track the real column from cumulative spans** (blank cells shift indexing — do not
  use the raw array index). The basic row is typically one `span:4` node. `classifyUpgrade(key,name)` → upgrade
  type by regex on the key/name (fallback `control` + a converter warning). Power `Description` →
  `powerTemplate.description`.
- **Careers:** `Careers.xml` → the `careers` map ordering; cross-check each spec's `career` (specs in no career
  → `career:null` universals).
- **Output:** a single `fad-catalog.js` (`Object.freeze`, **stable key ordering** so regenerated files diff
  cleanly; pretty-printed for readability — not perf-critical under `file://`).
- **Runtime:** Node script `tools/convert-catalog.mjs` using an XML parser (e.g. `fast-xml-parser`), run
  manually: `node tools/convert-catalog.mjs <path-to-DataSet/Data> > fad-catalog.js`. **Dev-time only** — not
  shipped to the sheet user.
- **Validation output:** print counts (`# careers`, `# specializations` incl. universals, `# force powers`,
  `# nodes`, `# edges`) plus any unclassified abilities / unresolved talents; **exit code 1** on any unresolved
  so the build fails loudly.
- **Licensing / fan-content:** do **not** commit copyrighted rulebook prose wholesale. The generated
  `fad-catalog.js` (which contains ability descriptions) should be treated as a **local build artifact** —
  `.gitignore` it, or commit a **names/structure-only** variant (descriptions blanked) for a public repo.
  Document this and include the FFG fan-content disclaimer in `README-fad-catalog.md`.

## 10. Risks & edge cases

1. **Script load order** — `<script src>` must come **before** the inline script (classic scripts run in
   document order) + runtime guard.
2. **`renderTrees` clears `#tree-container`** — never place Add controls inside it.
3. **Legacy trees without `instanceId`** — `migrateState` stamps ids so remove/dedupe/XP work.
4. **Blank force-power cells** shift column indexing — converter tracks real column from cumulative spans.
5. **Reciprocal edges** — emit Down/Right only; never both directions.
6. **Cross-tree node-id collisions** — currently harmless; suffix futureproofs (apply to ids + edge endpoints
   atomically).
7. **`xpSpent` was static/unused** — making it derived/readOnly changes its meaning; ensure no other writer.
8. **First specialization is free** — auto-surcharge must not charge the starting spec; gate behind override.
9. **Career-skill auto-apply deferred** — note-only in v1 to avoid mutating the skills grid.
10. **Licensing** — generated catalog contains rulebook prose; gitignore or ship names-only for public repos.
11. **Print fidelity** — every new control (`#treeControls`, `.tree-remove`, picker, `#xpWarning`) carries
    `.no-print`.
12. **Catalog vs saved-tree drift** — acceptable; runtime trees are self-contained and not re-resolved at render.
